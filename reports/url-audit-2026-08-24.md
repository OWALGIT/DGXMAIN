# URL & site audit — 24 Aug 2026

Full sweep of every HTTP-servable hostname across all four Cloudflare zones,
cross-referenced against Cloudflare Tunnel state and per-host `cloudflared`
configs on the fleet.

- **267 hostnames** audited (`inventory/sites.tsv`)
- **4 zones**: `yohay.ai` (170), `yohayai.com` (85), `owalai.com` (30), `annima.ai` (2)
- Raw results: `reports/url-audit-2026-08-24.tsv` — reproduce with `./bin/url-audit`

## Headline

**~96 hostnames (36%) are reachable. ~127 (48%) are broken.** The remaining 44
sit behind a Cloudflare Access login on a tunnel that is down — the login page
renders, but there is nothing alive behind it.

Almost all breakage traces back to **six root causes**, not 127 separate faults.

## Root causes, in priority order

### 1. Six Cloudflare Tunnels are down — 69 hostnames affected

`dgxmain`, `dgxsec`, `gama2`, `arcai-wp`, `garage1`, `hivemind-hub` all report
`down`. 25 hostnames return cf 1033 outright; another 44 are gated by Cloudflare
Access, which answers *before* the tunnel is consulted — so they show a login
page and then fail. Those are the deceptive ones: they look alive from outside.

On `dgxsec` the `cloudflared` service is `inactive`; the machine is instead
running the `bitfin-arena` tunnel from a token. Its own tunnel config is absent,
so the ~18 `*.yohayai.com` names pointing at it cannot resolve to anything.

Worst-affected names include `librechat.yohay.ai`, `portainer.yohay.ai`,
`dashboard.yohay.ai`, `web.yohay.ai`, `auth.yohay.ai`, `site.yohay.ai`,
`brain.yohay.ai`, `safescan.owalai.com`, and the whole `term-*`/`mdm-*`/`aster-*`
families on `yohayai.com`.

### 2. `5060ihome` carries 59 hostnames but serves 10 — 40 broken

DNS points 59 names at tunnel `117e8f06` (`5060ihome`), whose ingress list has
only 10 rules; the catch-all is `http_status:404`. Everything else 404s
(`NO_INGRESS`) or 502s (`SERVICE_DOWN`).

A second config at `/root/.cloudflared/config.yml` defines a *different* tunnel
(`2619016d`) with 11 more rules — `nomad`, `portainer`, `uptime`, `n8n`,
`webui`, `git`, `maas`, `dash`. That tunnel is **not running and has no DNS**,
which is very likely the missing half: those rules were written for names that
now resolve to `117e8f06`. Merging the two ingress lists into the running tunnel
would recover a large share of these in one change.

### 3. All 17 `*.vpsall.owalai.com` names fail TLS — 0 reachable

Every two-level name under `vpsall.owalai.com` fails the handshake
(`sslv3 alert handshake failure`), while `vpsall.owalai.com` itself returns 200.
Reproduced from two independent networks, so this is real and not a probe
artifact. A `*.vpsall.owalai.com` certificate does exist at the edge, but it is
not presented on these names' own resolution path — consistent with an
Advanced Certificate Manager cert that was ordered but never fully deployed.

Affected: `n8n`, `openwebui`, `librechat`, `litellm`, `dify`, `grafana`,
`portainer`, `keycloak`, `uptime`, `beszel`, `chroma`, `console`, `dokploy`,
`frigate`, `ha`, `nodered`, `astermcp`, plus `vpsall.ai1.owalai.com`.

### 4. Two origin servers are dead — 11 hostnames

- `162.19.126.209` — port 443 refuses connections. Takes down `7`, `acme`, `bo`,
  `customers`, `dev`, `k8s`, `servers`, `status`, `sw`, `wpbit` (`.yohay.ai`),
  plus `pbx`/`sip` which reset the connection.
- `34.45.166.153` — port 443 refuses connections. Takes down `api.owalai.com`
  and `grafana.owalai.com`.

Both verified unreachable from inside the fleet, so this is the origin, not
Cloudflare.

### 5. `dioneto` tunnel is missing five ingress rules

`n8n.`, `paperless.`, `portainer.`, `status.`, `vault.dioneto.yohay.ai` all 404.
The tunnel is healthy and its config (which lives on **`storai`**, not
`vps-dioneto`) routes the flat `dioneto-*` names correctly — the dotted variants
were never added.

### 6. `51.195.88.44` fails origin TLS — 4 hostnames

`ks8-aster`, `ks8-webui`, `nitay` (`.yohay.ai`) return cf 526, and
`controller.owalai.com` returns cf 523, though the host answers on 443.
`aster-gama2.yohayai.com` returns cf 525 from `213.32.69.7`. Origin certificate
is invalid or expired for these names.

## Two things that are working as intended

- **Geo-blocking.** Both zones carry a `ks7-geo-block` ruleset that blocks any
  non-Israeli source IP. `yohayai.com` blocks everything bar a 15-host
  allowlist; `yohay.ai` exempts all its own names. This initially read as 61
  broken sites — they are fine, just fenced. **Any external monitoring must
  probe from an Israeli IP** or it will report the whole `yohayai.com` zone as
  down.
- **Cloudflare Access.** 81 names sit behind `bitonpro.cloudflareaccess.com`.
  Note the caveat in §1: Access answers before the tunnel, so an SSO redirect
  proves the edge is configured, *not* that the backend is alive.

## Fleet-side notes

- **`vpsall` (100.68.77.46) is unreachable** — SSH times out, Tailscale last saw
  it 2026-08-09, 15 days ago. It still has DNS and a healthy `vpsall-yohay`
  tunnel, so some names resolve to a machine nobody can log into.
- The `dioneto` tunnel runs on `storai`, not on `vps-dioneto` — worth correcting
  in the inventory's mental model.
- `5060ihome` has no `curl` installed, which is why the Israeli-vantage probes
  in this audit were run with `python3`.

## Suggested order of work

1. Restart `cloudflared` on `dgxsec`, `dgxmain`, `gama2`, `arcai-wp` — recovers
   the largest block of names (69) for the least effort.
2. Merge the orphaned `2619016d` ingress rules into the running `5060ihome`
   tunnel — recovers up to 40.
3. Re-issue / redeploy the `*.vpsall.owalai.com` certificate — recovers 17.
4. Bring back `162.19.126.209` and `34.45.166.153` — recovers 11.
5. Add the five dotted `*.dioneto.yohay.ai` ingress rules — recovers 5.
6. Delete DNS for names that are genuinely retired, so the next audit is signal
   rather than noise.
